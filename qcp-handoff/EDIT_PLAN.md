# Focused edit plan

Maintain the three-problem scope. A change earns its place if it improves
understanding of a task, accuracy of a verdict, reliability of execution or the
quality of real demo footage.

## P0: execution and truth

1. Verify the Vercel production origin with a real Python submission. Use the
   production domain, not only the protected preview URL. Confirm public access.
2. Upload/test the Qollab ZIP. Confirm the Python bridge, catalog load, Run and
   Submit. Record its real URL and execution result. Investigate failures before
   claiming the Qollab path is verified.
3. Recheck startup, failure, retry and cancellation. Judge/network errors must
   leave contest penalties unchanged. Keep startup progress understandable.
4. Preserve explicit source labels and all query-model assumptions.

## P1: make the first attempt easier

1. Compare the current statement and editor with a student attempting A. Move
   the interface contract closer to the edit action if repeated scrolling causes
   confusion. Keep the full statement accessible.
2. Make the distinction between Run examples and Submit the full suite visible
   at the action point. Keep their histories and penalties distinct.
3. Make the first counterexample readable: input size, expected condition,
   observed success and one route to inspect the fixture.
4. Improve code editing only as needed: readable font, line numbers, indentation,
   keyboard shortcuts and robust draft preservation. A larger editor library is
   justified only if it works in both deployment paths and adds a needed benefit.
5. Add a narrow, optional visual explanation of phase kickback if it helps the
   error/correction scene. It must use correct amplitudes and avoid the claim
   that superposition lets users read all answers at once.

## P2: demonstrate competitive purpose

1. Show the local round's solve count and penalty near the relevant submissions.
2. Verify a reload preserves the started clock and the accepted draft.
3. Keep editorials locked during the local round and explain its honor-based
   scope. Do not build anti-cheat theater around public tests.
4. Preserve the Codeforces-style problem layout. Avoid adding a marketing hero
   that delays access to the editor.

## Product and business validation after the hackathon

Find one course or programming club willing to attempt this edition. Observe
first-Accepted time, full-suite submissions and whether people return for another
problem. Interview the organizer about authoring, grading and contest tasks.
Do not infer payment intent from a compliment or count AI-generated personas as
users. A useful next feature should follow a repeated problem in that pilot.

## Verification proportional to edits

Judge changes: run the QCP tests and compare affected browser/Qiskit results.
UI changes: run the focused workflow on desktop/mobile and inspect screenshots.
Packaging changes: inspect the ZIP entrypoint and verify import/call behavior.
Deployment changes: submit on the public origin. Do not rerun unrelated projects.

Regenerate `docs/qcp` with `tools/build_qcp_site.py` and the ZIP with
`tools/package_qcp.py` after relevant source edits. Package the updated handoff
only after its URLs and claims agree with the state of the project.
